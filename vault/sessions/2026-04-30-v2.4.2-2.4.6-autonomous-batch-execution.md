## v2.4.5 — B6 Backend security gate

### Probléma
`WorkerService.login()` a `dto.getBranchId()` érvényesítésekor csak 2 dolgot ellenőrzött:
1. Branch létezik
2. Branch ugyanahhoz a company-hoz tartozik

DE: nem ellenőrizte a `worker_branch_access` táblán keresztül, hogy a workernek van-e explicit hozzáférése a kért branch-hez.

### Eredeti fix (v2.4.5)
```java
boolean hasAnyAccess = !workerBranchAccessService.listBranches(workerId).isEmpty();
if (hasAnyAccess && !workerBranchAccessService.hasAccess(workerId, branchId)) {
    throw new AuthenticationException(...);
}
```

**Bug**: ha `listBranches()` üres → check átugrik → privilege escalation lehetséges.

## v2.4.6 — Codex P1 #331 privilege escalation fix

### Codex P1 finding (PR #331)
> The new gate only checks `hasAccess(...)` if `listBranches(workerId)` is non-empty, which means any worker with zero `worker_branch_access` rows can still log in with an arbitrary `branchId` from the same company. This creates a privilege-escalation path.

### Új logika (strict)
A kért branchId akkor és csak akkor engedélyezett, ha:
1. Explicit `worker_branch_access` rekord létezik a `(workerId, branchId)` párra, **VAGY**
2. A kért `branchId == worker.branchId` (default branch, legacy 1:1)

Egyéb esetben `AuthenticationException` → privilege escalation prevention.

### Tesztek (3 unit teszt)
- `login_branchOverride_nonDefault_noAccess_throwsAuthError` → DENY
- `login_branchOverride_defaultBranch_succeeds` → ALLOW (default = legacy 1:1)
- `login_branchOverride_explicitAccess_succeeds` → ALLOW (multi-branch worker)
