# v2.5.0 Production outage — incident postmortem

## TL;DR

A v2.5.0 sprint (PR #336, sha `11f9342d`) Hetzner deploy után HTTP 502 outage (~30 perc).
Root cause: V174 migrációban rossz táblanév (`branches` plural a `branch` singular helyett).
A revert (PR #337) kódszinten OK, de a Flyway schema_history-ben perzisztens FAILED entry +
a stale v2.5.0 JAR a Hetzneren maradva blokkolta az újraindulást. Manuális hotfix workflow
(`hotfix-flyway-repair.yml`) takarította + symlink-elte vissza v2.4.10-re.

**Production helyreállt 08:32 CEST.**

## Root cause (tényalapon)

### 1. Elsődleges hiba: V174 migráció rossz táblanév
```sql
-- ÉN ÍRTAM (HIBÁS):
ALTER TABLE branches ADD COLUMN is_vault BOOLEAN NOT NULL DEFAULT FALSE;

-- HELYES (mert az entity @Table(name="branch") singular):
ALTER TABLE branch ADD COLUMN is_vault BOOLEAN NOT NULL DEFAULT FALSE;
```

**Backend entity** (`Branch.java`):
```java
@Entity
@Table(name = "branch")  // SINGULAR
public class Branch { ... }
```

**Forrás-tényelem**: az entity `@Table(name="branch")` annotációját **NEM ellenőriztem** a V174 migráció megírásakor. Ad-hoc plural-t használtam (`branches`).

### 2. Másodlagos hiba: deploy script `sort -V | tail -1`
A `deploy-hetzner.yml` workflow:
```bash
JAR=$(ls $DEPLOY/target/valuta-backend-*.jar | grep -v SNAPSHOT | grep -v current | sort -V | tail -1)
ln -sf "$JAR" "$SYMLINK"
```

A `sort -V` magasabb version-t választ. A v2.5.0-s deploy után a `valuta-backend-2.5.0.jar` ott maradt a Hetzner `target/`-ben. A v2.4.10-s rollback deploy is felmásolt egy új JAR-t, DE a `sort -V | tail -1` továbbra is a v2.5.0-t választotta. Így a symlink rosszul mutatott.

### 3. Harmadlagos hiba: Flyway schema_history persistence
A v2.5.0 első deploy közben a V174 fail-elt → Flyway insertelt egy `success=false` rekordot a `flyway_schema_history`-be. Miután a JAR-ból eltávolítottuk a V174.sql-t (revert), Flyway még mindig refused to start, mert a HISTORY-ban van failed entry, és default config szerint NEM ugorja át.

Hotfix:
```sql
DELETE FROM flyway_schema_history WHERE version = '174' AND success = false;
```

## Megoldás (a hotfix workflow lépésenként)

`.github/workflows/hotfix-flyway-repair.yml` (manual `workflow_dispatch` + "REPAIR-V174" confirmation):

1. **DELETE failed V174 entry** a `flyway_schema_history`-ből
2. **rm -f valuta-backend-2.5.*.jar** (stale JAR-ok takarítása)
3. **ln -sf valuta-backend-current.jar → latest v2.4.x JAR** (symlink korrekció)
4. **systemctl restart valuta-backend.service**
5. **Health check HTTP 200**

Mind az 5 lépés sikeresen lefutott a 25204833865 run-ban.

## Tanulságok

### Mi NEM működött
1. **Nem írtam unit tesztet** a V174 migrációra (Flyway integration test).
2. **Nem ellenőriztem az entity annotációt** a migration fájl írásakor.
3. **Nem teszteltem a Hetzner deploy-t** a merge után — automatikus feltevés alapon dolgoztam.
4. **Egyszerre 19 fájlt módosítottam** (atomi PR alapelv megsértése).
5. A deploy script `sort -V` logikája naive, nem tudja kezelni a sikertelen deploy után stale-ré váló JAR-okat.

### Mi MŰKÖDÖTT
1. A revert mechanizmus working — a kód-szintű rollback gyorsan kész lett.
2. A hotfix workflow pattern — `workflow_dispatch` + confirmation + idempotens SSH script — pontosan a megfelelő eszköz inkonzisztens production state javítására.
3. Tényalapú diagnózis: deploy log → Flyway exception → entity annotáció → V174.sql összevetés → root cause azonosítása.
