## C) B6 SetupWizard branch-mismatch — security architecture

**Kontextus**: a desktop pénztáros app SetupWizard-jában kiválasztott `branch_code` **NEM propagálódik** a backend felé. A backend a `worker.branchId`-t használja (JWT claim), ezért:
- Ha KOSA worker BR017-en van regisztrálva, de a SetupWizard BR035-öt választ → a tranzakciók BR017-re kerülnek (a wizard választás IGNORE-olva)
- B6 + B24 ugyanaz a root cause

**Megoldási architektúra** (3 réteg):

### Backend (Spring Boot)

```sql
-- V173 migration
CREATE TABLE worker_branch_access (
  worker_id BIGINT REFERENCES worker(id),
  branch_id UUID REFERENCES branch(id),
  granted_at TIMESTAMP DEFAULT NOW(),
  granted_by_worker_id BIGINT REFERENCES worker(id),
  PRIMARY KEY (worker_id, branch_id)
);

-- Seed: minden worker-nek a default branchId-jához access
INSERT INTO worker_branch_access (worker_id, branch_id, granted_at, granted_by_worker_id)
SELECT w.id, w.branch_id, NOW(), w.id FROM worker w WHERE w.branch_id IS NOT NULL;
```

```java
@Service
public class WorkerBranchAccessService {
    public boolean hasAccess(Long workerId, UUID branchId) {
        return repo.existsByWorkerIdAndBranchId(workerId, branchId);
    }

    public UUID resolveTransactionBranch(WorkerAuthenticationDetails auth) {
        UUID overrideBranch = auth.getBranchOverride();
        if (overrideBranch != null && hasAccess(auth.getWorkerId(), overrideBranch)) {
            return overrideBranch;
        }
        if (overrideBranch != null) {
            log.warn("[BRANCH_GUARD] worker {} unauthorized branch override to {}",
                    auth.getWorkerId(), overrideBranch);
            throw new SecurityException("Branch access denied");
        }
        return auth.getDefaultBranchId();
    }
}
```

### JWT extension

A login response + JWT tartalmazzon `branchOverride: UUID` opcionális claim-et, amit a SetupWizard választás alapján a frontend küld a login request-ben.

### Frontend (penztar-client + frontend-react)

```typescript
// SetupWizard end-to-end flow:
// 1. Wizard: kiválasztott branch_code → SQLite config
// 2. Login API call: POST /auth/login { username, password, branchOverride: SetupWizardBranchId }
// 3. Backend validate + JWT issue
// 4. Frontend useAuthStore: store JWT + branchOverride
// 5. Backend transaction handler: resolveTransactionBranch(auth)
```

## E) B9 LISTAK.dll funkciók portolása — feature work

**Kontextus**: a legacy `LISTAK.dll` (Delphi/Pascal) 5-6 különböző report-ot generált, amit a modern web `/reports` aggregátor NEM tartalmaz teljesen. Az audit szerint hiányzik:

1. **Forgalom dekád** (10-napos forgalmi kimutatás)
2. **Időszaki kimutatás** (custom date range, multi-currency)
3. **Kezelési díj dekád** (10-napos handling fee summary)
4. **Pillanatnyi készlet** (snapshot a jelenlegi időpontra, current stock)
5. **Kiadott valuták** (worker × currency × date range)
6. **Eladott valuták** (ugyanaz, sell side)
7. **ATVETT BANKJEGY** (received banknotes — bank → vault)
8. **ATADOTT BANKJEGY** (delivered banknotes — vault → bank)

### Implementációs terv

**Backend** (új endpoints):
- `GET /api/v1/reports/turnover-decade?branchId=X&decade=2026-Q2-1`
- `GET /api/v1/reports/period-summary?from=YYYY-MM-DD&to=YYYY-MM-DD&currency=EUR`
- `GET /api/v1/reports/handling-fee-decade?branchId=X&decade=...`
- `GET /api/v1/reports/stock-snapshot?branchId=X&timestamp=YYYY-MM-DDTHH:MM:SS`
- `GET /api/v1/reports/issued-currencies?from=...&to=...&workerId=Y`
- `GET /api/v1/reports/banknote-receipts?type=RECEIVED&from=...&to=...`

**Service**: új `ReportService.java` ~500-700 LOC, query builder pattern.

**Frontend**: új `/reports/turnover-decade`, `/reports/period`, etc. oldalak. Egységes `ReportFilterPanel` komponens (date range, branch select, currency select).

**Test**: per-report unit + integration test (a Hungarian banking compliance miatt minden számítás verifikálandó NGM 23/2014 + pénzmosás törvény szerint).

## F) i18next library setup — Sourcery #320 P3

**Kontextus**: a 2026-04-29 autonóm session 4 ad-hoc i18n batch (v2.3.55-58) ~12 fájlt javított ékezet-szempontból. Sourcery P3 felhívta a figyelmet, hogy egy **központi i18n resource** sokkal robusztusabb. Ez a v2.4 sprint design-decision része.

### Implementációs terv

**Library**: `react-i18next` + `i18next` + `i18next-browser-languagedetector`

**Setup**:
```typescript
// frontend-react/src/i18n/index.ts
import i18n from 'i18next'
import { initReactI18next } from 'react-i18next'
import LanguageDetector from 'i18next-browser-languagedetector'
import hu from './hu.json'
import en from './en.json'

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: { hu: { translation: hu }, en: { translation: en } },
    fallbackLng: 'hu',
    interpolation: { escapeValue: false }
  })
```

**Resource fájl** (kezdő, ~200-300 string):
```json
// hu.json
{
  "common": {
    "save": "Mentés",
    "cancel": "Mégse",
    "edit": "Szerkesztés",
    "delete": "Törlés"
  },
  "cashier": {
    "buy": "Vétel",
    "sell": "Eladás",
    "conversion": "Konverzió",
    "storno": "Sztornó"
  },
  ...
}
```

**Migration plan**:
1. Setup `react-i18next` + `i18next-browser-languagedetector`
2. Resource fájl `hu.json` létrehozása az össze létező magyar string-ből (~30-50 fájl)
3. Komponensekben `useTranslation()` hook + `t('cashier.buy')` pattern
4. Linter rule: új JSX szöveg-literál tilos (csak `t()` hívás)

**Migration nehézsége**:
- Sok JSX-string (esp. `placeholder="..."`, `<th>...</th>`, `toast.success("...")`)
- Dinamikus string-ek (`${value} Ft`) — `t()` interpolation szintaxis
- Test-ek mock-olása

### Becslés

- Setup: 0.5 nap
- Resource fájl + migration ~50 fájl: 1-1.5 nap (incremental, NEM blocking)
- Linter rule + CI gate: 0.5 nap
- **Összesen: ~1-2 nap (NEM blocking, parallelizálható)**
